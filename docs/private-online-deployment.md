# Private online deployment: household handoff

This is deployment preparation, not a completed deployment or production-security approval. No hosting account, paid resource, network enrollment, public listener, DNS record or Google grant was created. Existing local accounts, database and keys must remain untouched. No real data belongs in staging.

## Recommendation and cost (checked 10 November 2026)

Start with a private test site restricted to the household, then validate a separate household installation. Keep one Node/SQLite backend instance and the existing encrypted vault engine. Do not put SQLite on a serverless/ephemeral filesystem, shared network filesystem or multiple replicas. Both computers connect to the same HTTPS backend; normal access does not require copying database files between computers or a working Google Drive connection. Drive provides the separate sync/backup integration. Changes on another open client may require Refresh vault; concurrent writes retain the existing revision checks.

## Private access and owner experience

Tailscale Serve is the proposed optional access boundary, **not activated or required by the existing application**. The maintainer creates a private network and a policy allowing only the two approved users/devices to reach the Lockbox node on HTTPS port 443. Do not retain an unrestricted default network policy or expose unrelated devices. Do not use Funnel, public tunnels or router port forwarding. Public inbound application ports stay closed; maintainer SSH access is separately restricted. No backend, recovery-helper or Caddy admin port is exposed.

The owner and partner each install the connection app and accept their own private network invitation once, then open the same secure address in Chrome and use separate Lockbox username/login and master passwords. Network enrollment does not replace Lockbox authentication or require either person to share the administrator's Google account. The maintainer handles enrollment support and device revocation. If even a connection app is unacceptable, browser-only public access is a separate exposure decision and is not authorized here.

[Serve](https://tailscale.com/docs/features/tailscale-serve) supplies trusted TLS and keeps access within the private network. It forwards to loopback-only Caddy, which serves built frontend assets and proxies API requests to loopback-only Node. Do not forward Serve directly to Node (it does not serve the frontend), to Vite, or to a source directory. Certificates disclose the generic hostname in public certificate-transparency logs even though the application is private. Use no personal names in the machine name. [HTTPS details](https://tailscale.com/docs/how-to/set-up-https-certificates).

## What is protected, and what is not yet verified

- Production mode requires a single HTTPS origin and private absolute storage paths outside the release. Authentication uses Secure, HttpOnly, host-only `__Host-` cookies, SameSite=Lax, server-side session expiry/revocation, exact Origin/CSRF checks and existing abuse limits. Do not loosen them for the VPN or trust VPN identity headers as a login bypass.
- Saved credential/folder contents and vault keys are client encrypted; login passwords are Argon2id hashes. **SQLite itself is not SQLCipher/full-file encrypted.** Account metadata, hashes and some operational records remain readable to an authorized database reader. Provider-encrypted persistent block storage is an additional deployment requirement. It does not protect against a compromised running host/provider or maliciously replaced frontend JavaScript.
- Server keys and backend OAuth tokens are protected by existing file permissions/key binding; OAuth token contents are encrypted. Google secrets never go in frontend builds, ingress configuration or task arguments. The private ingress account receives only nonsecret port/static-path configuration, not the backend environment file.
- Automatic complete backup creation, encryption, restore verification and separate-folder Drive delivery are implemented. Until Google is connected and a real off-device restore succeeds, local backups alone are **not** disaster recovery. Keep the emergency backup key separately offline; preserve each account's login recovery code and vault recovery key. Loss-of-all-proof limits still apply.
- Automated two-account tests establish server scoping, independent personal keys and explicit Household grants plus a private transfer key. An invitation to register alone grants no Household access. Both users must be tested on their actual computers. Revocation cannot recall copied secrets or old snapshots.

## Automated maintainer preparation

`npm run deployment:prepare -- --profile staging --hostname <actual-device>.<actual-tailnet>.ts.net --output <new-private-directory>` generates protected production-mode configuration and matching backend/ingress systemd units. `--profile household` selects a separate installation. The hostname is syntax checked only; ownership, enrollment, DNS, certificate and Google acceptance are **not** implied. Missing hostname/account authorization is an external prerequisite, not something to fabricate.

| Profile   | Application / data / OS account                                       | Backend / ingress |
| --------- | --------------------------------------------------------------------- | ----------------- |
| staging   | `/opt/lockbox-staging`; `/var/lib/lockbox-staging`; `lockbox-staging` | 8788 / 8081       |
| household | `/opt/lockbox`; `/var/lib/lockbox`; `lockbox`                         | 8787 / 8080       |

The generator reads no live database or credentials, does not initialize a vault, and refuses a nonempty output directory. It intentionally includes **no Google credentials**. `npm run deployment:prepare -- --verify <private-directory>` verifies the generated files; modified plans fail closed. Generated files are not source-controlled. Transfer the protected plan through the maintainer's trusted channel; do not post its future secret-bearing files in chat.

After checking an approved Linux target, the maintainer stages an allowlisted release at its matching `/opt` directory, installs locked runtime dependencies on that platform and prepares a separately mounted encrypted persistent volume at the matching `/var/lib` directory. Both code and runtime dependencies must be root-owned, readable by the service/Caddy and unwritable by service accounts. Do not copy the Windows node_modules tree. No disk formatting, account purchase or provider enrollment is performed by the scripts.

`sh deploy/install-private-linux.sh <absolute-private-plan-directory>` checks Node 24, Caddy, the mount/filesystem, plan integrity and systemd definitions. It refuses altered/linked existing config, provisions using the existing database/key helper and installs matching units without starting/enabling them. It never copies the local database, keys, invitations or grants. Its mount check does **not** prove provider encryption: the maintainer must retain provider-side evidence. Staging and household use different OS accounts/data/config locations; preferably use a dedicated staging host for fault/restore experiments.

Only after private-network setup is approved, the maintainer validates the actual policy, confirms no existing Serve/Funnel mapping will be replaced, starts the intended backend and ingress units, and points **Serve** at `http://127.0.0.1:8081` for staging or `:8080` for household. Certificate/enrollment approval is not automated. Verify that turning off the private connection on a second device makes the site unreachable. Do not publish a real URL or claim deployment completion before these checks.

First-owner provisioning produces a private one-use administrator invitation, not public first-claim registration. Staging uses new fictional test accounts and independently generated keys. Never restore a real household backup into staging, reuse an existing Google grant, seed real passwords, reset the local database or silently promote staging data into production. Preserve the existing local installation separately; any later migration needs a verified backup, isolated restore and explicit data-migration authorization.

## Google developer requirements still missing

No usable developer OAuth client configuration is currently available. The maintainer must enable Drive API v3 in the appropriate Google project; supply a confidential Web application client ID/secret; configure accurate consent branding/support/privacy/audience; and register the exact deployed origin plus `/api/drive/callback`. Recovery also needs the existing private helper callback `http://127.0.0.1:18888/callback`. Keep test and household registrations/grants separate.

The adapter requests `https://www.googleapis.com/auth/drive`, a restricted scope required by the current arbitrary existing-folder workflow. The maintainer must document whether this strictly personal two-user deployment qualifies for Google's personal-use exception; otherwise the applicable verification and possibly external security-assessment obligations apply. Do not promise verification is free, silently reduce permissions or tell users to bypass warnings. Testing-mode external clients generally have seven-day refresh-token expiry for this scope; it is not a reliable permanent backup setup. [Scope guidance](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [verification and exceptions](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [token lifetime](https://developers.google.com/identity/protocols/oauth2/).

The maintainer must additionally establish that Google accepts the proposed private `ts.net` redirect/branding domain for the applicable use case. Do not assume ownership of that provider's domain or promise domain verification. If an owned domain is needed, arrange it and private TLS/DNS through the maintainer before Drive acceptance, without exposing the app. [Google domain/production policies](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance). This is separate from the owner merely approving Google consent in Lockbox Settings.

## Release gates and what the owner must do

The release run exposed a real startup limit: under load, mandatory authentication initialization exceeded Fastify's default 10-second plugin timeout, causing the Drive fixture's initial setup and dependent checks to fail. The isolated Drive suite passed all 20 checks. Startup now has a bounded 60-second plugin budget, a 90-second readiness deadline and a 120-second systemd start budget. A regression check delays a required plugin beyond the old limit and proves that health is withheld until it completes. This does not change Argon2 parameters, the 10-second request timeout, session expiry, CSRF or abuse limits. An actual Linux/load rehearsal remains required.

Maintainer gates: real Linux/systemd restart and storage-detach behavior; HTTPS/cookies/CSP; forbidden-origin and unauthenticated access; two physical devices/private-network denial; separate Personal vaults and explicit Household sharing; concurrent edits/refresh; real Google consent/refresh/revocation/reconnection; separate-folder automatic backup delivery; fresh-server remote restoration of both accounts/vaults; recovery and offline key custody; disk/failure alerts; independent security review and remediation. Record PASS/FAIL/NOT RUN without secrets. The existing extension remains an excluded candidate.

The owner chooses only whether private testing is acceptable and approves any later budget/deployment proposal. Once supplied with a validated private address, both users accept their own network invitation, register through their private Lockbox invitations, save their recovery information, and use the app. Only the administrator approves the Drive connection and grants Household access. No owner terminal, developer console, database commands, environment editing or hosting-dashboard configuration is required.

Current decision: **private fictional-data staging is the next practical target; real-password production is not yet approved.** No reachable private staging URL or production address has been created by this preparation.
